# 下一代通用 Agent Runtime

## 文档性质

本文定义 Suna 面向下一代 Agent 的长期方向。它不是当前实现说明，不是功能清单，也不承诺具体 API、工具名或开发顺序。当前行为始终以 `docs/` 和代码为准。

本文要回答的核心问题是：

> 当模型持续变强、能够自主理解目标、规划行动和组织协作时，Suna 应提供怎样一副最小而完备的“身体”，才能让同一个通用 Agent 感知和操作真实世界，同时始终处在用户授权与可靠 Runtime 的边界内？

## 长期愿景

Suna 的目标不是复刻当前流行的 Coding Agent、多 Agent 公司或 Agent OS，而是成为一个：

> **本地优先、模型自主、用户可控、长期连续的通用 Agent Runtime。**

同一个 Suna 应能根据用户输入、上下文和外部事实，自主选择合适的工作方式：

- 直接交流，不强行任务化；
- 阅读、修改和验证代码；
- 调研、整理、创作或操作本地环境；
- 在必要时询问用户；
- 临时委派一个或多个隔离执行单元；
- 等待用户、时间或外部世界发生变化后继续；
- 在真正需要用户注意时主动沟通。

这些不是预设的 Agent 类型或 Session 模式，而应是强模型基于同一组通用能力自然形成的行为。

## 核心架构观点

### 模型是大脑，Suna 提供身体

模型负责：

- 理解用户和环境；
- 识别目标与约束；
- 制定、调整或放弃计划；
- 判断是否调用工具、询问用户或进行委派；
- 临时定义分工、身份和协作结构；
- 选择需要读取、共享或忽略的上下文；
- 判断何时回应、等待或主动联系用户。

Suna Runtime 负责：

- 向模型提供真实、明确、有来源的输入和上下文；
- 暴露感知和操作真实世界的通用能力；
- 执行用户授予的权限与模式，不依赖模型自觉守界；
- 维护会话、运行、等待、恢复、并发和持久化事实；
- 保证工具调用、事件、错误和副作用可以观察与审计；
- 通过稳定协议让不同客户端接入同一个 Agent；
- 在模型请求结束、客户端断开或进程重启后维持必要的连续性。

Suna 不应成为第二个大脑。Runtime 不应因为当前模型能力不足，就永久固化任务分类、难度判断、固定规划、角色组织或工作流步骤。

### 少约束认知，严格约束影响范围

Suna 应尽量减少对模型思考方式的规定，同时严格维护模型影响真实世界的边界。

应减少和避免：

- 巨型 system prompt；
- 强制 Plan / Act / Reflect 流程；
- “复杂任务必须 spawn”等行为规则；
- Runtime 关键词分类和难度判断；
- 固定的 Planner、Executor、Reviewer 角色；
- 固定 Agent 公司组织图；
- Coding、Research、Assistant、Emotion 等硬编码模式。

应长期强化：

- 工具与数据访问权限；
- Workspace 和敏感资源边界；
- 用户确认与可撤销性；
- Subtask 最小授权与上下文隔离；
- 预算、并发、超时和取消；
- 状态持久化、恢复和事件归属；
- 结果验证、来源、证据与副作用披露。

原则是：

> **不规定模型如何思考，但明确模型能够影响什么。**

### 追求 Primitive Complete，而不是 Feature Complete

Suna 不追求内置所有业务场景。长期目标是以尽可能少、正交且可组合的能力，覆盖模型可能需要的行为维度。

可用下面六个维度检查 Runtime 是否完备：

1. **感知（Perceive）**：读取用户输入、文件、图片、网络、MCP 数据和外部事实。
2. **行动（Act）**：修改文件、执行命令、调用服务、创建成果和影响环境。
3. **沟通（Communicate）**：回复、询问、请求确认，以及在合适时机主动通知用户。
4. **委派（Delegate）**：创建临时、隔离、最小授权的执行单元，并汇总结果。
5. **记忆与回忆（Remember / Recall）**：维护用户与会话连续性，并按需发现相关历史。
6. **等待与继续（Wait / Resume）**：跨越单次模型请求，等待用户、时间、外部事件或其他执行结果后继续。

这些是能力维度，不等于必须新增六个工具。每次演进应优先复用现有协议、状态和工具体系，只有缺少真正通用的原语时才增加新概念。

## 一个 Agent，多种自然行为

Suna 始终是一个通用 Agent，不按用途拆成不同内核。

- 用户要求修改代码时，它自然表现为 Coding Agent。
- 用户希望讨论情绪、选择或生活时，它可以只交流，不调用工具、不创建任务。
- 用户交给它复杂调研或工程问题时，它可以临时并行委派，表现出多 Agent 协作能力。
- 外部客户端传入值得处理的事实时，它可以判断是否行动、等待或联系用户。

Session 不是固定的工作类型。不同 Session 可以有不同 cwd、历史、权限和上下文边界，但不应先验标注为某种 Agent 模式。模型应根据实际输入决定行为。

## 编排的长期形态

Suna 可以支持编排，但不固化编排策略。

### 模型负责组织，Runtime 负责执行事实

主模型可以临时决定：

- 自己直接完成；
- 并行委派多个独立方向；
- 使用不同模型或工具；
- 给执行单元分配临时身份和背景；
- 等待部分结果后再继续委派；
- 交叉验证或取消无价值的分支。

Runtime 应提供必要的隔离、权限、并发、状态、取消、结果回传和可观察性，但不内置“经理 Agent”“开发 Agent”“测试 Agent”等长期角色。

所谓多 Agent 公司，只应是模型在复杂任务中临时生成的一种协作形态，而不是 Suna 的固定产品结构。

### Subtask 的演进判断

当前 Subtask 已体现正确方向：独立上下文、显式任务与背景、明确模型、工具白名单和副作用披露。

未来如果真实场景要求更长时间或更动态的协作，应优先增强通用执行能力，例如：

- 可观察进度；
- 独立取消；
- 有界并发和预算；
- 通过显式引用交换结果或成果；
- 必要时等待其他执行完成。

是否需要长期执行句柄、动态补充上下文或跨 Run 协作，应由真实需求验证，不能提前把 Subtask 扩展成复杂任务平台。

## 上下文、隔离与动态共享

模型越强，越应该由模型决定当前需要哪些信息；但 Runtime 不能把所有历史自动合并。

长期应保持下面的分离：

- 用户长期偏好和约束；
- 当前 Session 对话；
- Workspace / 项目事实与历史决策；
- 当前执行的临时状态；
- Subtask 的隔离上下文；
- 文件、图片、报告等外部成果。

共享应采用“发现后显式引用”，而不是隐式继承全部上下文：

1. 模型发现可能相关的历史、记忆或成果；
2. 模型决定是否读取；
3. Runtime 检查权限、范围和大小；
4. 进入请求的信息保留来源；
5. Subtask 只获得主模型明确传递或授权读取的内容。

这同时保护：

- 注意力质量；
- 隐私与隔离；
- 稳定前缀和缓存命中；
- token 成本；
- 信息来源与可纠正性。

不应通过固定 Session 类型决定共享策略，也不应允许模型无条件读取所有 Session。

## 记忆与“越来越懂你”

Suna 的长期记忆不是完整聊天仓库，也不应成为不可审查的黑盒画像。

长期成立的原则：

- 主要保存稳定的偏好、沟通方式、工作习惯、约束、纠错和用户事实；
- 区分用户明确表达、系统推断和纠错信号；
- 每条记忆具有来源、证据、置信度、范围、时间和删除能力；
- 项目事实、任务状态和用户画像不能混成同一类记忆；
- 模型使用记忆时应尽量保持相关、少量和缓存友好。

“自我进化”不意味着 Agent 可以静默修改自己的核心代码或安全边界。更可靠的含义是：

- 根据用户的重复选择和纠正持续校准行为；
- 发现记忆冲突时修正或缩小适用范围；
- 将稳定、可复用的方法沉淀为 Skill；
- 对自身代码的改进仍经过隔离修改、测试、审查、用户批准和发布。

未来值得研究的是记忆的反馈闭环，而不是无限增加记忆数量：

```text
用户信号 → 提取 → 使用 → 用户反馈 → 强化 / 修正 / 降权 / 过期
```

## 时间连续性与主动性

Suna 当前主要由用户消息启动一次 Run。面向未来，通用 Agent 需要逐步跨越单次请求的时间边界，但不能因此变成内置业务调度器。

### 高置信度判断

未来 Agent 会需要：

- 等待用户稍后回答；
- 等待构建、CI、下载或外部服务；
- 暂停与继续；
- 客户端断开后保留必要执行状态；
- 接收来自外部世界的新事实；
- 在真正需要用户注意时发起沟通。

具体是否表现为 `wait` 工具、可持久 Run、事件信箱或其它协议，需要在设计时结合实际场景决定。规划只确认“时间连续性”是通用能力维度，不提前承诺具体 schema。

### 主动性不是不断找活

主动性的质量取决于时机，而不是频率。

一个成熟 Agent 应能在获得外部事实后自主决定：

- 忽略；
- 静默记录；
- 等待更多信息；
- 在下次相关对话中提出；
- 立即通知用户；
- 在授权范围内先执行，再汇报；
- 请求用户做关键决定。

Suna 不应默认周期性调用模型寻找任务，也不应内置所有 watcher、cron、邮件、GitHub 或日历集成。上层客户端可以感知具体系统；Runtime 只在出现可复用需求时提供最小、结构化、可追踪的输入与恢复能力。

## Runtime 与客户端边界

Suna 的 daemon 和 protocol 是长期架构资产。TUI 只是一个客户端，不是 Agent 能力本身。

Runtime 应负责：

- Agent、模型、工具、Guard、记忆和执行状态；
- 输入与事件的统一业务语义；
- 状态持久化和恢复；
- 对外通知、错误与能力发现；
- 多客户端看到同一个 Agent 与同一份事实。

客户端应负责：

- TUI、IDE、Web、移动端、语音或 IM 的交互形态；
- 具体外部系统的监听与接入；
- 通知投递和注意力界面；
- 将用户操作和外部事实转换为 protocol 输入。

但“Suna 不做上层编排”不是绝对规则。模型驱动的通用编排属于 Agent 能力，可以由 Runtime 承载；特定业务的触发器、固定流程和展示策略应留给客户端或扩展。

## 能力进入核心的判断标准

每个新能力在进入 Suna 前，应同时回答：

1. **它是否扩展模型的感知、行动、沟通、委派、记忆或时间连续性？**
2. **它是否为多个场景复用，而不是只服务某个产品故事？**
3. **它是否在替模型做本应由模型完成的认知决策？** 若是，应优先不做。
4. **能否复用现有 Tool、Provider、Protocol、Media、Memory、Run 或 Guard 机制？**
5. **权限、生命周期、失败、取消、恢复、并发和资源边界是否明确？**
6. **是否保持模型上下文和 tool schema 稳定、紧凑、缓存友好？**
7. **是否可以被 TUI 和第三方客户端一致理解，而不泄漏 UI 语义到核心？**
8. **如果未来模型更强，这个抽象仍然有价值，还是会成为脚手架负担？**

只有当答案足够明确，才进入具体实现设计。

## 应避免的方向

除非出现无法由通用原语解决的强需求，Suna 不应把以下内容固化进核心：

- Coding / Research / Assistant / Emotion 等 Agent 类型；
- 固定 Agent 角色和组织架构；
- Runtime 内置的任务难度分类和黑盒模型路由；
- 固定 Planner / Executor / Reviewer 流程；
- 自动合并所有会话和项目上下文；
- 针对单一 SaaS 或业务的 watcher 与 workflow；
- 无预算、无停止条件的后台自治；
- 依赖巨型 prompt 维持的行为规则；
- 把营销上的“Agent OS”当成架构目标。

## 演进优先级

规划不设固定发布日期，但演进顺序应遵守以下优先级。

### 第一层：保持现有 Runtime 可靠

持续维护当前主链路：

- 模型请求和工具循环；
- 上下文、压缩、缓存与 token 预算；
- Guard、Workspace 和敏感边界；
- Session / Run 状态、事件归属与恢复；
- Subtask 隔离、授权和结果语义；
- Protocol 的稳定性和第三方可理解性；
- TUI 性能与交互，但不把 UI 语义下沉核心。

任何未来能力都不能以破坏这层可靠性为代价。

### 第二层：验证时间连续性

优先通过真实场景研究：

- 等待用户和外部结果；
- 暂停与恢复；
- 客户端断开或进程重启后的连续执行；
- 多个执行同时存在时的资源和状态边界。

这一阶段研究的是通用执行事实，不先实现任务看板、定时器产品或 Agent 公司。

### 第三层：验证可控的上下文发现与共享

研究模型如何按需发现历史 Session、项目事实、记忆和成果，同时保持明确 scope、来源、授权与预算。默认隔离，按需引用，不做全局上下文倾倒。

### 第四层：验证主动沟通

只有在具备可靠状态、等待恢复和注意力边界后，才验证外部事实输入与主动联系用户。衡量标准不是“Agent 是否主动”，而是“它是否在正确时机提供了真实价值且没有造成噪音或越权”。

这些层次不是功能承诺。每一层都可以因模型能力、用户需求或工程成本变化而调整。

## 成功标准

Suna 的长期成功不以工具数量、内置角色、工作流数量或“Agent OS”标签衡量，而以以下问题衡量：

- 同一个 Agent 能否自然处理交流、编码、调研和复杂协作，而无需切换固定模式？
- 模型能否自主选择直接执行、询问、委派、等待或停止？
- Runtime 是否用少量原语支持这些行为，而没有复制模型的认知能力？
- 用户是否始终知道并控制 Agent 可以访问和影响什么？
- 执行是否可观察、可取消、可恢复、可验证？
- Agent 是否能在长期使用中更准确地理解用户，而不形成不可纠正的画像？
- 新模型变强时，Suna 是否自然获得更强能力，而不是被旧脚手架限制？
- 第三方客户端是否能基于同一协议构建新的交互和编排形态？

最终目标是：

> **能力丰富但原语凝练，模型自主但权限可控，长期连续但不制造噪音，Runtime 可靠但不替模型思考。**
